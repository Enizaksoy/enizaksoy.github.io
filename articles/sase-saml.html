SASE-SAML

SAML authentication against Microsoft Entra ID, worked end to end — the message flow, what every profile field really does, and packet captures from a failing and a working run that differ by exactly one line.

A SASE client registration failed with a message that points squarely at authentication:

Could not complete authentication. Please try again.

Authentication had in fact succeeded. Entra ID validated the user, signed the assertion and handed it to the browser. The flow broke on the next step — the browser could not deliver that assertion, because the hostname it was told to POST to did not exist in DNS. Adding one DNS record fixed it.

Placeholders: this write-up uses generic values — example.com as the domain, <gw-a>/<gw-b> for the two gateway addresses, and <tenant-id> for the Entra directory ID. Substitute your own.

1. Why the error message is misleading

SAML POST binding is a front-channel protocol. The Service Provider (the SASE gateway) and the Identity Provider (Entra ID) never contact each other. Every message travels through the user's browser as an HTTP redirect or an auto-submitting form POST.

Two consequences follow, and both matter more than they first appear:

  • The gateway needs no outbound access to Entra ID, and Microsoft never needs inbound access to the gateway. All network requirements sit on the client.
  • Entra ID cannot observe whether the flow completed. Its work ends when it hands the form to the browser — so a fully successful Entra sign-in log proves nothing about the last steps.
"The IdP side is clean" is not evidence. In the failing run below, Entra ID recorded a successful sign-in while the login was already dead.

3. The message flow

1.  browser   --- HTTPS 443 --->   GATEWAY      portal / SSE login page
2.  browser   <-- 302 redirect ---  GATEWAY      "go to Entra ID" + SAMLRequest
3.  browser   --- HTTPS 443 --->   ENTRA ID     user authenticates
4.  browser   <-- HTML form ------  ENTRA ID     auto-submit, action = ACS URL
5.  browser   --- HTTPS POST --->  GATEWAY      SAMLResponse (the assertion)
6.                                 GATEWAY      validates signature + Destination
7.  browser   <-- session -------   GATEWAY      login completes

The browser talks to the gateway twice (steps 1 and 5) and to Entra ID once (step 3). The two servers never talk to each other at all.

Step 4, in detail

Entra ID does not redirect the browser back. It returns an HTML page whose only job is to make the browser POST the assertion onward:

<html>
 <body onload="document.forms[0].submit()">
  <form method="POST" action="https://acs.example.com/...">
    <input type="hidden" name="SAMLResponse" value="PHNhbWxwOlJlc3BvbnNl...">
    <input type="hidden" name="RelayState"   value="...">
  </form>
 </body>
</html>
Illustrative, not captured. This form is the standard SAML 2.0 HTTP-POST binding shape, reproduced from the specification. The real bytes travel inside TLS to Entra ID and were not decrypted in this test — to capture them, set SSLKEYLOGFILE before launching the browser and point Wireshark at that key log, or use a SAML tracer extension.

The onload attribute submits the form immediately. Submitting a form means opening a new HTTP connection to the address in action. A browser cannot connect to a name — only to an IP address — so it must resolve that name first. This is step 5, and this is where a missing DNS record stops everything.

4. The SAML profile — which fields are real destinations

saml-profiles <PROFILE>
    host                  https://acs.example.com
    single-signon-url     https://login.microsoftonline.com/<tenant-id>/saml2
    sp-entity-id          https://vendor.example.net/metadata
    idp-entity-id         https://sts.windows.net/<tenant-id>/
    idp-x509-certificate  <local-cert-object>
    id-prefix             AD
    group-attribute       member
    unified-acs-uri       enabled
FieldWhat it identifiesIs it ever connected to?
hostThe SP itself — base of the Assertion Consumer Service (ACS) URLYes — by the BROWSER, at step 5
single-signon-urlThe IdP sign-in endpointYes — by the browser, at step 3
sp-entity-idSP identity string; must match Entra's "Identifier (Entity ID)"No — label only
idp-entity-idIdP identity string, used to validate the issuerNo — label only
idp-x509-certificateLocal certificate object used to verify the assertion signatureNo — stored locally
group-attributeName of the group claim inside the assertion—
unified-acs-uriUse a unified ACS URI for SAML requests—
Three of these look like URLs but are never visited. Only host and single-signon-url are network destinations. An unreachable sp-entity-id is harmless; an unreachable host breaks the login. This distinction sends a lot of people to fix the wrong field.
Do not omit group-attribute. Without it the assertion's group claim is never read, so authentication succeeds while group-based policy receives nothing and silently matches no rule.

5. The host field, in detail

The CLI schema describes it only as Versa-flexvnf host value. What it actually does: it is the base address used to build the ACS URL — the address the browser returns to after Entra ID authenticates the user. It is the return address the gateway stamps on the request before sending the user away.

It lands inside the AuthnRequest the browser carries to Entra ID:

<samlp:AuthnRequest
     Destination                 = "https://login.microsoftonline.com/<tenant-id>/saml2"
     AssertionConsumerServiceURL = "https://acs.example.com/..."      <-- from host
     ...>
   <saml:Issuer>https://vendor.example.net/metadata</saml:Issuer>
 </samlp:AuthnRequest>
Illustrative, not captured — reproduced from the SAML 2.0 specification to show where the value lands. The request itself is carried inside TLS.

The same string must appear in three places

LocationField name
Gateway SAML profilehost
Entra ID app registrationReply URL (Assertion Consumer Service URL)
Browser POST after authenticationform action / assertion Destination

If they do not match, Entra ID returns AADSTS50011 and the user never comes back.

Why the gateway has to be told its own address

A server does not know the name by which the outside world reaches it. The gateway knows itself by its interface address; it has no way to learn that clients call it acs.example.com. NAT, load balancers and DNS all sit in between — so the external name is configured by hand.

The gateway never dials this address. It uses the value twice, both times as a string: it writes it into the AuthnRequest for the browser to read, and it string-compares it against the Destination/Recipient field of the returned assertion, rejecting the assertion on a mismatch.

So the gateway performs no DNS lookup for this name. It listens on it — it does not call it. The browser is the only party that resolves it, which is why every check belongs on the client.

        -> browser gives up. No POST is ever sent.

Everything before the NXDOMAIN is green. The portal opened, the browser reached Entra ID, the user was authenticated. Entra ID returned the auto-submit form — which means the ACS URL passed its Reply URL check, so the string side of the configuration was already correct. No AADSTS50011 was raised.

The eight identical queries are the browser's normal retry behaviour before it gives up. The failure is one missing DNS record, nothing else.

8. A cross-gateway ACS works

The working capture shows something worth recording. The session started on one gateway and the assertion was delivered to a different one, because the ACS hostname resolved only to the second:

session started    ->  GW-A     (portal, AuthnRequest issued here)
assertion POSTed   ->  GW-B     <-- different gateway
session completed  ->  GW-A     (browser returns, login succeeds)

It still succeeded: GW-B accepted the assertion and sent the browser back to GW-A to complete the session.

This disproves the session-affinity concern raised before the test. With unified-acs-uri enabled, the ACS URL does not have to resolve to the gateway that issued the AuthnRequest — so a tenant-wide, round-robin FQDN is usable as the ACS host in this configuration.

9. Troubleshooting — two failure modes that look nothing alike

CauseSymptomEntra ID sign-in logWhere to fix
ACS string mismatchAADSTS50011 shown to the usershows the errorEntra Reply URL, or the host value
ACS name not resolvablebrowser stalls; client reports an authentication errorshows a SUCCESSFUL sign-inDNS, verified from the client

The second case is the misleading one. Because Entra ID's work finishes at step 4, its logs look perfectly healthy while the flow is dead.

10. Two diagnostic traps

Resolve-DnsName and nslookup are not the same test

PS> Resolve-DnsName acs.example.com -Server <dns-ip>     -> FAILS
PS> nslookup        acs.example.com  <dns-ip>            -> resolves fine

Resolve-DnsName goes through the Windows DNS Client service and obeys the Name Resolution Policy Table (NRPT) even when -Server is given. nslookup builds its own query and bypasses NRPT entirely.

When the two disagree, the fault is in the client's policy layer, not on the DNS server.

This was hit during the same investigation. A disconnected SASE client had left stale NRPT rules behind — the catch-all rule pinned every unlisted name to a public resolver the client could not reach, so names explicitly listed resolved while everything else timed out:

Namespace                 NameServers      <-- left behind after the tunnel went away
---------                 -----------
.corp.example.com         <internal-dns>
gw-a.example.com          <internal-dns>
portal.example.com        <internal-dns>
.                         8.8.8.8          <-- catch-all: everything else goes here
PS> Get-DnsClientNrptPolicy                                  # inspect
PS> Get-DnsClientNrptRule | Remove-DnsClientNrptRule -Force  # clear (admin)
PS> Clear-DnsClientCache
NRPT rules can outlive the tunnel. The VPN adapter was gone from Get-NetAdapter while its name-resolution policy was still in force — so "the VPN is disconnected, therefore its settings are not in effect" is not a safe assumption on Windows.

tcpdump does not see the gateway data plane

tcpdump -i any on the gateway captured zero packets during a run that demonstrably carried traffic. The data-plane interfaces are bound to DPDK and are invisible to the Linux kernel.

Never read an empty capture taken this way as "no traffic arrived." Use a client-side capture, or the platform's own capture facility.

11. Checklist for a new SAML profile

  1. Set host to a resolvable FQDN that points at a gateway.
  2. Register the identical string in Entra ID as the Reply URL (ACS URL).
  3. Verify resolution from the client, not from the gateway — the gateway never resolves this name.
  4. Confirm the client trusts the CA that signs the certificate presented at that name.
  5. Match sp-entity-id to Entra's "Identifier (Entity ID)", or expect AADSTS700016.
  6. Set group-attribute, or group-based policy receives nothing.
  7. Compare against a known-good profile in the same tenant before troubleshooting from scratch — four fields differed between the working and the test profile here, and each one was a separate failure mode.
The one-line summary. In SAML POST binding every network requirement is on the client. If the login stalls and the IdP log looks clean, resolve the ACS hostname from the client machine before looking anywhere else.
