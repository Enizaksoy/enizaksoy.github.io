Borrowed Probes

Versa keeps SLA state per probed forwarding class. A class that has no probe of its own borrows another class's probe by a fixed order — and that borrowed row, not the class your QoS policy assigned, decides which WAN circuit the session takes. Lab on VOS 22.1.4: delay injected on the NC probes only, four data classes measured, three fixes compared.

The problem

A spoke is connected to hub-controllers. By default the spoke probes the hubs on forwarding class fc_nc every 10 s (the To_Controller term of the SLAM path policy). The operator wanted faster SLA detection and added a second probe on fc_be every 2 s. Then the transport provider started adding delay only to CS6-marked packets — which is exactly what the NC probes carry. The result on the spoke:

INET-1 INET-1 fc_nc    priority "SLA Violated"
INET-1 INET-1 fc_be    priority "Priority 1"
MPLS-1 MPLS-1 fc_nc    priority "Priority 2"
MPLS-1 MPLS-1 fc_be    priority "Priority 2"

Data traffic is mapped to fc6 and fc_be. Some flows stayed on the Priority 1 circuit, others moved to Priority 2. Three questions came out of this:

  1. Which probe does a flow in fc6 follow when there is no fc6 probe — fc_nc or fc_be?
  2. Can all traffic be made to follow the BE probes? The NC probes cannot be disabled.
  3. Many sites have very low bandwidth; the operator does not want to enable more probes.

The rule

SLA state is kept per (local circuit, remote circuit, forwarding class), but only for forwarding classes that actually have a probe configured. When a session arrives in a class with no probe, the forwarder picks the SLA row of another class in this order:

  1. A probed class in the same traffic class. Traffic class = FC ÷ 4: NC = {fc_nc, fc1, fc2, fc3}, EF = {fc_ef, fc5, fc6, fc7}, AF = {fc_af, fc9, fc10, fc11}, BE = {fc_be, fc13, fc14, fc15}.
  2. Otherwise, the first probed class found in a fixed neighbour order:
Session's traffic classBorrow orderExercised in this lab
EF (fc_ef, fc5, fc6, fc7)same TC → NC → AF → BEsame TC (Test B, D); EF→NC (Test A)
AF (fc_af, fc9–fc11)same TC → BE → EF → NCAF→BE (Test A); AF→EF when BE absent (Test D)
BE (fc_be, fc13–fc15)same TC → AF → EF → NCBE→EF when AF absent (Test D)
NC (fc_nc, fc1–fc3)same TC → EF → AF → BEnot exercised (NC always had a probe)
Two consequences. (1) fc6 is in the EF traffic class, so with only fc_nc and fc_be probed it borrows the NC row — that is why fc6 flows moved to Priority 2 while fc_be flows stayed. (2) The often-repeated rule "an unprobed class follows the nearest equal-or-higher class" is wrong for AF and BE: AF borrows from BE first, BE borrows from AF first. There is no configuration knob for this order; the specific-config container of a path-policy term only holds the SLA-monitoring interval/adaptive leaves.

Lab

CML 2.10, VOS 22.1.4. Spoke BRANCH-1 with two WAN circuits (INET-1 on vni-0/0, MPLS-1 on vni-0/1) connected to three hub-controllers HUB-1/2/3; org ACME. A Linux host behind the spoke (10.1.11.10) sends four flows to a hub LAN address (10.1.1.1), one per forwarding class. Outputs below are from BRANCH-1 unless stated; where the three hubs show identical values only the HUB-1 rows are kept.

To delay the NC probes and nothing else, the spoke's INET link was re-cabled through an Ubuntu bump host bridging two interfaces (br0), with a prio qdisc and a u32 filter on the ToS byte:

Why four services in four classes: the question is about inheritance, so one flow per traffic class is needed — fc6 (the operator's class, EF traffic class), fc_ef (same traffic class, to show they behave alike), fc_af (AF, never probed in any test) and fc_be (its own probe). A QoS rule without set action allow is rejected at commit ('... set action' is not configured).

Probe rows and their outer DSCP

After the commit, sla-monitor status has an fc_nc and an fc_be row per circuit pair to each hub. The SLA PDUs are 192-byte VXLAN-GPE packets on UDP 4790; each class carries its own fixed outer DSCP, which is what lets a provider delay one class selectively:

bump$ sudo tcpdump -c 24 -nn -v -i eth1 udp and port 4790
IP (tos 0xb8, ttl 255, ...) 192.0.2.241.4790 > 192.0.2.26.4790: VXLAN-GPE, vni 32787    # hub -> spoke, fc_ef probe (EF)
IP (tos 0x0,  ttl 255, ...) 192.0.2.26.4790 > 192.0.2.244.4790: VXLAN-GPE, vni 34097   # spoke -> hub, fc_be probe
bump$ sudo tcpdump -c 8 -nn -v -i eth1 'udp and port 4790 and (ip[1] & 0xfc) == 0xc0'
IP (tos 0xc0, ttl 255, ...) 192.0.2.26.4790 > 192.0.2.241.4790: VXLAN-GPE, vni 34097   # spoke -> hub, fc_nc probe (CS6)

Measured mapping: fc_nc = 0xc0 (CS6), fc_ef = 0xb8 (EF), fc6 = 0x88 (AF41, seen in Test B), fc_be = 0x0.

Test C: re-mark the NC probes on the WAN (works, with a side effect)

set orgs org-services ACME class-of-service rw-rules dscp NC-REMARK forwarding-class fc_nc loss-priority high code-point be

Why EF is the right class for the second probe. With one extra probe you want every data class to land on it. EF is the only class that all three other data classes reach before NC: AF and BE both fall through to EF once their own neighbour is absent, and the EF traffic class reaches it directly. A BE probe, by contrast, is reached by AF but not by EF — EF goes to NC first, which is the operator's symptom. Only the NC class itself keeps following fc_nc, and that is control-plane traffic. This answers questions 2 and 3: all data traffic follows a single 2 s probe, without adding one.

Each direction is decided separately

The spoke's To_Controller probes decide only spoke→hub path selection. Hub→spoke is decided by the hub's own probes toward branches, i.e. the hub's To_Branches term. In this lab the hubs' To_Branches already carries fc_ef at 2 s adaptive (the orchestrator default), so the return direction was already "EF-steered" and nothing had to change there. If an operator changed the hub side to fc_be as well, the same move to fc_ef applies on the hubs.

Branch-to-branch traffic is governed by each branch's To_Branches term, which the To_Controller change does not touch.

Reading path-state correctly

A frequent misreading: path-state is not "one row per data class". It lists one row per probed class per circuit pair. With probes {fc_nc, fc_be} there is no row for fc6, fc_af or fc_ef; a session in one of those classes is evaluated against a borrowed row by the order above, and the only place that shows the outcome is the session table (tx-wan-ckt). To see the full chain for one flow:

show orgs org ACME sessions sdwan detail | select source-port | select forward-fc | select tx-wan-ckt | select forward-sdwan-rule-name
show orgs org-services ACME sd-wan policies Default-Policy rules path-state brief <rule>

Note also that sessions established before a violation is declared keep their circuit; the forwarding profile in this lab has no evaluate-continuously, so every result above was taken on flows restarted after the state change.

Timing notes

  • With a 10 s NC probe the "SLA Violated" state was declared 3 min after the delay started; after each path-policy commit it took 5.5–8 min to be re-declared, because a commit on the path policy resets the SLA state for every row.
  • After the NC probes recovered (Test C), path-state still showed "SLA Violated" 3 min later; the clear is slower than the declare and was not timed to the end.
  • Right after a WAN re-cable the path state briefly showed "SLA Violated" with zero metrics; it cleared on its own within about 5 min.

Summary

  • A session in an unprobed forwarding class is steered by a borrowed probe: same traffic class first, then EF→NC→AF→BE, AF→BE→EF→NC, BE→AF→EF→NC, NC→EF→AF→BE. Not configurable.
  • With probes {fc_nc, fc_be}, EF-class data (fc_ef, fc6) follows the NC probe; AF-class data follows BE. That is the split the operator saw.
  • Cheapest fix with the same probe count: probe fc_ef instead of fc_be. Every data class then follows the EF probe; only NC-class traffic follows fc_nc.
  • Alternatives: a dedicated probe per data class (more probes), or a DSCP rewrite of fc_nc on the affected WAN (removes CS6 from control traffic too).
  • Check both ends: spoke To_Controller for spoke→hub, hub To_Branches for hub→spoke.
