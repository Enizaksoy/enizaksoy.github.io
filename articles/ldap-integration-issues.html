AD / LDAP Integration Issues

Why Active Directory integration fails on a SASE gateway, how to read the logs, and the one group trap that bites nearly everyone — worked as an ordered resolution chain.

2026-08-05 · troubleshooting · Active Directory · LDAP · group mapping
On this page

Versa SASE (and most VPN/SASE products) never truly "know" Active Directory — they run ordinary LDAP operations against it. Almost every AD integration problem is one broken link in a strict, ordered chain, and a failure high in the chain hides everything below it. Fix top-down.

Placeholders: this guide uses generic values — domain example.com (base DC=example,DC=com), DC at <dc-ip>, a bind service account svc-ldap-bind, and a sample user alice. Substitute your own.

The single most useful diagnostic — how full the group table is tells you which link broke:
show orgs org-services <ORG> user-identification ldap-server-data groups brief
Empty = base DN bad (link 3) · only a profile line = bind failing (link 2) · full object list = links 1–5 OK.

2. Where to look — logs & resultCodes

The authoritative source for user-identification LDAP is one file on the gateway:

tail -f /var/log/versa/versa-ip2user.log
Log messageMeaningBroken linkAction
resultCode(49) Invalid credentialsBind rejected2 — BindFix bind DN/password. Not routing — TCP already connected.
resultCode(34) Invalid DN syntaxMalformed DN3 — Base/Bind DNCheck comma-vs-dot in the DN
resultCode(32) No such objectDN valid but absent3 — Base DNSet base to defaultNamingContext
resultCode(8) Strong auth requiredAD LDAP signing enforced1/2 — TransportUse LDAPS (636) / enable SSL
i2u_ldap_authenticate: User <x> not foundUser search returned nothing4 — Search attrMatch user-name to the login format
(no bind line at all)Nothing reached the DC1 — ReachabilityCheck route / routing-instance / firewall
resultCode(49) is not a routing problem. A bind failure means the TCP session to the DC was already established and LDAP rejected the credentials. Don't chase routes/tcpdump on a 49 — go straight to the bind DN and password.

5. user-name vs login format — the #1 auth gotcha

Two independent things must line up: the attribute you configure must be populated on the account, and the value the client sends must equal that attribute exactly.

Client logs in as…Set user-name to…Requires in AD
alice (short name)sAMAccountNamealways present
alice@example.com (UPN)userPrincipalNameUPN must be set (often blank on built-ins)
Which way to fix it: the name in the "not found" line tells you. Short name not found with user-name=userPrincipalName → switch to sAMAccountName (or log in with the UPN). If unsure, use sAMAccountName + short-name login — every account has one; UPN is optional.

6. Primary vs secondary groups — the #1 group-policy trap ★

Never gate SASE policy on "Domain Users" (or any primary group). It is every user's primary group, and AD does not store primary membership in the attributes LDAP tools read — so the match fails for every user. Use a dedicated secondary group.

Every AD user has exactly one primary group plus any number of secondary groups. They are stored completely differently, and only secondary membership is visible to LDAP membership resolution.

KindStored whereAttributesResolvable?
Secondary (normal "Add…")on both objectsgroup.member AND user.memberOf✅ yes
Primary (default Domain Users, RID 513)only on the user, as an integeruser.primaryGroupID; NOT in member/memberOf❌ no

member vs memberOf — don't confuse them

AttributeLives onLists
memberthe group objectDNs of users in the group — this is what group-member must be
memberOfthe user objectDNs of groups the user is in — a user attribute, not a group attribute

Proof from live AD (raw attributes)

# user "alice" (a member of a secondary group VPN-Users; primary = Domain Users)
(sAMAccountName=alice):
  primaryGroupID : 513                                   <- = Domain Users (her PRIMARY group)
  memberOf       : CN=VPN-Users,CN=Users,DC=example,DC=com   (secondary)
                   *** Domain Users is NOT listed ***

# group Domain Users (primary)
(cn=Domain Users):  member : <empty>                       <- alice not here; primary membership isn't stored

# group VPN-Users (secondary)
(cn=VPN-Users):     member : CN=alice,CN=Users,DC=example,DC=com   <- real, two-way link

alice is in Domain Users (primaryGroupID 513), yet neither alice.memberOf nor DomainUsers.member mentions it. VPN-Users shows the normal two-way link. The gateway walks member/memberOf → it matches VPN-Users and misses Domain Users.

A/B test (same user, same everything else)

Policy groupResult
CN=VPN-Users,… (secondary)register → 200, client connects
CN=Domain Users,… (primary)register → 403, "not allowed to connect…"

To enumerate a primary group you need a special query

# member is empty for a primary group; get its members via primaryGroupID:
(&(objectClass=user)(primaryGroupID=513))     # 513=Domain Users, 512=Domain Admins, 515=Domain Computers
Rules. (1) Group-based policy → always a dedicated secondary group (e.g. VPN-Users) that users are explicitly added to. (2) group-member=member, never memberof. (3) The policy's group reference must match a group-include-list entry exactly (full DN) — a short-name↔DN mismatch throws "illegal reference".

7. Verify from the AD side (before blaming the gateway)

Reproduce what the gateway does — a bind + a search — from any Windows box, no RSAT required (built-in .NET ADSI):

# PowerShell — base DN, bind test, and a user's real attributes
([ADSI]"LDAP://<dc-ip>/RootDSE").defaultNamingContext        # e.g. DC=example,DC=com

$u="EXAMPLE\svc-ldap-bind"; $p="<bind-password>"
$de = New-Object System.DirectoryServices.DirectoryEntry("LDAP://<dc-ip>/DC=example,DC=com",$u,$p)
$ds = New-Object System.DirectoryServices.DirectorySearcher($de)
$ds.Filter="(sAMAccountName=alice)"
$r=$ds.FindOne(); $r.Properties["primarygroupid"]; $r.Properties["memberof"]

$ds.Filter="(cn=VPN-Users)"; $ds.FindOne().Properties["member"]   # secondary → lists the user
$ds.Filter="(cn=Domain Users)"; $ds.FindOne().Properties["member"] # primary  → empty

ldapsearch equivalent: ldapsearch -H ldap://<dc-ip> -D "EXAMPLE\svc-ldap-bind" -w '…' -b "DC=example,DC=com" "(sAMAccountName=alice)" primaryGroupID memberOf

8. Step-by-step troubleshooting flow

  1. Reproduce and read versa-ip2user.log while the user logs in.
  2. Decode the resultCode/message (§2) to find the broken link.
  3. resultCode(49) → fix the bind account (Case C); verify the bind from a PC first (§7).
  4. "User not found" → check user-name vs login format (§5) and that the attribute is populated.
  5. Empty groups/users brief → fix base-DN commas + domain-name (Cases A/B).
  6. Groups pulled but policy denies → check group-name/group-member (Case D) and the primary-group trap (§6).
  7. Still "not allowed" after auth succeeds → it's a secure-access policy problem, not LDAP (portal & gateway policies are separate — both must permit the user).
  8. After every change: commit, then re-check ldap-server-data and the log. Success is silent in ip2user.log (it records errors only) — confirm via the session history instead.
Two independent caches. A newly created AD group appears in the appliance's ldap-server-data after a group-mapping refresh (a config commit forces it immediately), but the orchestrator/manager keeps a separate cached group list for building policy. Refresh both, or the group is visible on the device yet unselectable in the policy UI.
