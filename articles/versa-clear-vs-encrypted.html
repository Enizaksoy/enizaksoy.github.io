Clear vs Encrypted Tunnels

Versa builds every branch both a clear and an encrypted overlay tunnel over the same circuits. Here is how to steer one flow onto the clear tunnel, three independent proofs of clear vs encrypted on the wire, and where the keys actually live — plus a Wireshark dissector patch for VOS 23.x.

A Versa SD-WAN fabric encrypts the overlay by default. But look at a branch's tunnel table and you find two tunnels to every peer — one clear, one encrypted — riding the same circuits. This walks a lab test that puts one flow on the clear tunnel and one on the encrypted tunnel, side by side, and proves the difference three ways: from the session table, from the packet length, and byte-by-byte in the capture. Then it answers the question that follows — if the data is encrypted, where is the key, and why can't someone with the capture decrypt it?

1. The dual-tunnel model

Every remote site is reachable over two overlay tunnels built on the same circuits: a clear one (VXLAN, no ESP) and an encrypted one (adds IPSec-ESP). Each has its own tunnel-endpoint address.

PeerClear TEPEncrypted TEP
Hub-110.53.0.810.53.0.9
Hub-210.53.0.1410.53.0.15
Controller10.53.0.310.53.0.2
Branch-A / B / C10.53.0.4 / .6 / .1810.53.0.5 / .7 / .19

The encapsulation chains differ by exactly one layer:

clear      :  VXLAN  +  MPLS-over-GRE  +  VMLH                +  inner IP     (52 B)
encrypted  :  VXLAN  +  IPSec-ESP  +  MPLS-over-GRE  +  VMLH  +  inner IP  (101 B)

By default the branch's routes resolve to the encrypted endpoints, so all user data is encrypted; the clear tunnels stay up but carry only SLA-probe traffic until a policy steers data onto them.

2. Forcing a flow onto the clear tunnel

Encryption per flow is a forwarding-profile knob — encryption always | never | optional — applied by an SD-WAN policy. Here only traffic to 9.9.9.9 is scoped to clear; everything else stays encrypted.

# address object for the one destination we want in clear
set orgs org-services SDWAN objects addresses Q9 ipv4-prefix 9.9.9.9/32
# forwarding profile that disables ESP
set orgs org-services SDWAN sd-wan forwarding-profiles CLEAR-TEST encryption never
# steer traffic to 9.9.9.9 through that profile
set orgs org-services SDWAN sd-wan policies Default-Policy rules CLEAR match destination address address-list Q9
set orgs org-services SDWAN sd-wan policies Default-Policy rules CLEAR set forwarding-profile CLEAR-TEST
commit

A client behind the branch LAN (10.10.10.100) then pinged both targets — real transit sessions through the SD-WAN, not device-originated traffic (a router-originated ping does not create the same org session).

4. Proof #2 — packet length on the wire

Same 300-byte ping payload to both targets, same hub. The encrypted flow's overlay packet is consistently larger by the ESP overhead.

FlowOn-wire lengthIn the capture
clear · 9.9.9.9394 B10 packets
encrypted · 8.8.8.8430 B13 packets

The +36 B is the AES-GCM ESP overhead — 8 B ESP header + 8 B IV + 16 B ICV + padding. Same payload, one is 36 bytes heavier: that is the encryption, visible as pure size. (Use a small, non-fragmenting payload — a 1000-byte ping fragments differently on the two tunnels because their MTUs differ, muddying the comparison.)

5. Proof #3 — byte-level decode

Both packets share the outer IP/UDP/VXLAN header. They diverge right after the Versa VMLH header — one exposes the inner packet, the other an ESP blob.

# CLEAR — to 9.9.9.9 (394 B)
VXLAN-GPE :  1c 91 03 fb ...            VNI 0x6b11, next-proto 0xfb (Versa)
VMLH 16B  :  12 08 00 05 ...           flag byte 05 = CLEAR
inner IP  :  45 00 .. 0a 0a 0a 64  09 09 09 09
             src 10.10.10.100   dst 9.9.9.9   proto ICMP
ICMP      :  08 00 ..                   type 8 = echo request
payload   :  61 62 63 64 65 66 ..  "abcdefghij..."
             inner IP + ping data FULLY READABLE — no encryption
# ENCRYPTED — to 8.8.8.8 (430 B)
VXLAN-GPE :  1c 91 03 fb ...            identical outer
VMLH 12B  :  12 08 00 fc ...           flag byte fc = ENCRYPTED
ESP hdr   :  5a 49 00 0c 00 04 0d 29    SPI 0x5a49000c, seq
IV        :  e3 98 24 87 d4 9b 2d 13
ciphertext:  57 bf b0 15 79 eb 26 ed ..
             8.8.8.8 absent, "abcde" absent — inner is ENCRYPTED
The tell. The VMLH flag byte discriminates: 0x05 = clear (16-byte header, then inner IP), 0xfc = encrypted (12-byte header, then an ESP header + ciphertext). Across the whole capture, every clear packet contained the inner destination and the "abcde" ping pattern; not one encrypted packet did.

6. Reading it in Wireshark

Wireshark decodes the outer VXLAN-GPE but stops at Next Protocol: Unknown (251) — a Versa-proprietary value — and shows the rest as raw Data. Versa publishes a Lua dissector (versa_vxlan_dissector.lua) that picks up from there. Drop it in %APPDATA%\Wireshark\plugins (Windows) or ~/.config/wireshark/plugins (Mac) and reload Lua plugins; on newer Wireshark change its line [3] from Dissector.get("eth") to Dissector.get("eth_withoutfcs").

Version drift — patch needed for VOS 23.x. The stock dissector maps next-proto 0xFC=ESP / 0xFD=GRE / 0xFE=VMLH, but 23.x packets carry next-proto 0xFB (251), which it does not handle — so the outer header decodes while the inner still falls to Data. A one-branch patch fixes it: on 0xFB, read the VMLH flag — 0x05 → skip 16 B → hand to the IP dissector; 0xfc → skip 12 B → hand to ESP.

Get the patched dissector: versa_vxlan_dissector_23x.lua — the stock Versa dissector plus the 0xFB branch. Replace the installed copy with it (two copies double-define the proto and error out).

With the patch, tshark unfolds both flows completely:

7. Where the keys live

If the encrypted flow is unreadable in the capture, where is the key — and could someone with the capture decrypt it? No, and the reason is architectural.

Branch-to-branch uses no IKE

A branch has exactly one IKE security association, and it is to the Controller — not to any peer branch. Six encrypted peers, one IKE SA. Branch-to-branch tunnels are never negotiated on the wire; there is no per-tunnel handshake to capture.

Keys are Diffie-Hellman, distributed over MP-BGP

The Controller is a custom multi-instance MP-BGP route reflector. Two kinds of information ride that one session:

CarriedAddress family / NLRI
LAN route reachability — RD, route-target, VRF labelVPNv4 / L3VPN · AFI/SAFI 1/128
Security-association / key material, PKI, transport & NAT stateVersa proprietary SD-WAN NLRI

The keys themselves are Diffie-Hellman values: each side holds a private DH key, computes the shared secret from the peer's public value distributed by the Controller, and the secret is never transmitted. Per-peer unique keys (N-1 per branch), so one compromised device never exposes the whole fabric. Data-plane cipher: ESP AES128-GCM.

SA and SPI, in one line

  • SA — Security Association: a one-way agreement on how to protect traffic — cipher, key, auth, anti-replay window, lifetime. Unidirectional, so each peer has an inbound and an outbound SA. All SAs live in the device's SAD in memory.
  • SPI — Security Parameter Index: a 32-bit number that names an SA. It rides in the ESP header so the receiver knows which SA/key to use — an index, not a key. In SPI names the SA for packets arriving here; Out SPI is the peer's inbound SPI, stamped on packets we send.

Enforcement is stateless "receive & check"

There is no session setup. An arriving ESP packet is matched against the pre-installed SA — and dropped if it doesn't match.

Identity is the certificate, not the IP. Spoofing a branch's IP fails: with no valid device certificate the impostor never forms the control channel, so it receives no SA — and any forged ESP it sends fails the receiver's ICV check. The trust anchor is the cert presented to the Controller at onboarding.

8. Takeaways

  • Clear = zero protection. Inner IP and payload are readable by anyone on-path, and there is no ESP integrity either — use it only on trusted transport, never on the internet.
  • Encrypted = content protected, metadata still leaks. A capture reveals who talks to whom, when and how much (and the SPI), but not the content.
  • You cannot decrypt from a capture. The SPI is an identifier; keys are DH-derived, computed locally, distributed by the Controller, and never traverse the data plane.
  • One flag byte decides. In the overlay header, VMLH 0x05 vs 0xfc is the whole difference between a packet anyone can read and one only the two endpoints can.
